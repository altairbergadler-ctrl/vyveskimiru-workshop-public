## Реализованный механизм

Один живой DOM, один экземпляр существующих скриптов и прежний путь редактора.
Сохранены все 143 исходных ID; всего 161 ID, дубликатов нет. Все десять исходных
script подключены по одному разу, добавлен `interface.js`. Ограничения input
и оба исходных inline style-блока сохранены.

`assets/interface.css` и `assets/interface.js` задают оформление и навигацию
над исходными узлами. Корневые атрибуты `data-interface="legacy|redesign"`
и `data-interface-step="1..4"` управляют четырьмя шагами
«Фото → Масштаб → Вывеска → Результат». CSS скрывает разделы других шагов,
сохраняя редакторские `[hidden]`, значения полей и обработчики. Готовность
берётся из действующих модулей, а не из посещения шага.

Кнопка «Прежний интерфейс» возвращает полную компоновку исходного редактора;
«Новый интерфейс» вновь включает шаги. Переключение не делает reload,
не заменяет DOM через `innerHTML`, не восстанавливает проект повторно,
не меняет ID выполняющегося задания и не отправляет POST. Фото, геометрия,
линейка, все три вида изделий, исходный PNG, история, экспорты, CorelDRAW
и наблюдение за результатом остаются в прежних модулях.

Дополнительные поля свёрнуты под «Для производства». Раздел меняет видимость,
сохраняя материалы, глубину, шрифт и другие значения. При переключении через
API активное поле и выделение сохраняются; поле с фокусом временно остаётся
видимым до ухода фокуса.

После изменения размеров рабочей области контроллер отправляет обычный
`resize` существующему viewport. Абсолютный zoom и центр сохраняются,
а режим «Вписать» адаптируется к доступной области. Ограничения края и
допустимого zoom могут подогнать вид, сохраняя координаты и размеры проекта.
Контроллер не записывает проект напрямую. Цепочка `viewport.configure` →
`signage:viewchange` → `draft.schedule` может сохранить изменившийся вид
в IndexedDB через существующее автосохранение. Отсутствие любых draft writes
при переключении не обещается.

Оформление выбирается при открытии:

- `?interface=legacy` — прежнее;
- `?interface=redesign` — новое;
- без валидного параметра — сохранённое предпочтение, затем новое по умолчанию.

Query имеет приоритет над предпочтением и не переписывается переключателем.
Ключ `localStorage` — `signage-interface-v1:<basePath>`, отдельно от проекта
и IndexedDB-черновика. Отказ чтения/записи storage не блокирует переключение.

## Восстановление и fallback

Начальное HTML-оформление — `legacy`. Новые кнопки скрыты и отключены,
пока не завершены `SignageDraft.ready` и `SignageGeneration.ready`.
Дополнительное продолжение promise даёт существующему модулю генерации
восстановить pending ID до выбора стартового шага. Ранний pointerdown/click
на новых кнопках блокируется до document capture, чтобы не отменить
восстановление черновика как пользовательское редактирование.

Pending и открываемая история начинают с шага 4. Незавершённые действия
`reference`/`measure` сохраняют шаг 2, `place`/`target` — шаг 3.
Валидный исходный `restoreJob` запоминается до удаления query владельцем
истории; также учитывается реальный статус открытия проекта/фото.
Поздний `resultchange` обновляет статусы, сохраняя выбранный пользователем шаг.
Контроллер оформления не начинает дополнительное восстановление или I/O.

Если новый JS не загрузился, начальное оформление остаётся прежним.
Если при инициализации отсутствует CSS sentinel либо получено событие ошибки
stylesheet, контроллер возвращает `legacy` и скрывает новые кнопки.
Прежние поля остаются доступны. Новые CSS/JS разрешены сервером как отдельные
статические маршруты; относительные API-пути и строгий CSP сохранены.
Runtime DCLogic/React из образца и `new Function` для переноса дизайна не нужны.

## Возврат оформления с сохранением текущей работы

1. В уже открытом новом редакторе нажмите «Прежний интерфейс». Фото, неполные
   точки, поля, оригиналы PNG и текущее задание остаются в той же странице.
   Reload, экспорт и очистка storage для этого не нужны.
2. Для обратного перехода нажмите «Новый интерфейс». Не создавайте новое
   задание для получения прежнего результата: текущий ID продолжает проверяться.
3. При следующем открытии можно использовать `calibrator.html?interface=legacy`
   или `calibrator.html?interface=redesign`. Изменение адреса через навигацию
   обычно перезагружает страницу; для незавершённой открытой работы пользуйтесь
   кнопкой. При сохранённом query он снова имеет приоритет после reload.
4. Перед закрытием/перезагрузкой дождитесь «Черновик сохранён». Для валидного
   проекта можно дополнительно сохранить JSON, исходное фото и оригинальный PNG.
   Незавершённые проекты поддерживает черновик; обычный JSON-экспорт требует
   успешного расчёта. Данные браузера для возврата не очищайте.

## Серверный возврат из тега при будущем развёртывании

Этот порядок предназначен для будущего выпуска после отдельного разрешения
на публикацию. В локальном этапе серверный откат не выполнялся.

1. Сначала используйте переключатель оформления: он сохраняет текущую работу
   без смены сервера. Для возврата самого кода проверьте live-выпуск, отсутствие
   выполняющейся генерации и актуальную закрытую резервную копию истории.
2. Подготовьте исходный код в отдельном checkout, сохраняя рабочую ветку
   и её незакоммиченные изменения. Из корня текущего worktree:

   ```powershell
   git rev-parse interface-before-redesign-20261010
   git worktree add --detach ../interface-rollback-products-v1 interface-before-redesign-20261010
   ```

   Ожидаемый SHA — `6785d0f1fe72f6049c48c37539854e1006bfabcf`. Не выполняйте
   reset/clean в worktree локального прототипа ради получения старых исходников.
3. Используйте проверенный сохранённый образ `channel-letter-mockups:20261010-products-v1`,
   если он соответствует baseline. При отсутствии образа соберите отдельный
   образ из checkout тега, с новым уникальным `APP_VERSION`, и проверьте его
   с изолированными данными. Подготовьте отдельный каталог выпуска на VPS
   по [DEPLOYMENT.md](../DEPLOYMENT.md); исторические каталоги vps8 там не являются
   baseline этого UI-отката.
4. Сохраните Compose-проект `signage-editor`, оба файла
   `compose.host-proxy.yaml` + `compose.password.yaml`, loopback-порт 18880,
   `/signs/`, действующий внешний auth-файл и постоянные тома
   `signage-editor_data` и `signage-editor_codex_home`. Не заменяйте историю
   старым снимком и не используйте `down -v`. Схема проектов этим UI-этапом
   не менялась; baseline products-v1 поддерживает те же v1/v2.
5. После завершения активного задания, штатной остановки и проверенной копии
   истории выберите прежний образ через `APP_VERSION` в закрытой конфигурации
   подготовленного выпуска. Из его каталога на VPS примените только app:

   ```sh
   docker compose -f compose.host-proxy.yaml -f compose.password.yaml config --quiet
   docker compose -f compose.host-proxy.yaml -f compose.password.yaml up -d --no-build app
   docker compose -f compose.host-proxy.yaml -f compose.password.yaml ps
   ```

6. Проверьте health, вход, прежний frontend, чтение существующей истории
   и проект/фото в браузере. Черновик остаётся в том же browser origin и pathname;
   не очищайте его. Внешний Caddy и основной сайт не меняются. Сохраните образ
   нового выпуска до завершения проверки возврата.
