вход в ChatGPT проверен после перезапуска контейнера. Выполнена одна реальная
генерация на Linux: двухстрочная надпись, исходное фото и исходное освещение;
задание успешно завершено, PNG сохранён. Независимое сравнение подтвердило

совпал с сохранённым по SHA-256. На момент первоначальной проверки в истории
подтверждены 7 записей. Результат просмотрен:
надпись читается в двух строках, лицевая часть синяя, борта светлые. [Открыть тестовый результат](https://vm-app.ru/signs/calibrator.html?restoreJob=vps-smoke-18b1dad9-3082-4d1f-b40f-fa83602d72ed).

оба файла: `-f compose.host-proxy.yaml -f compose.password.yaml`. Второй включает
встроенный вход и монтирует закрытый JSON только для чтения. Обычный
`compose.yaml` запускает второй Caddy и конфликтует с существующим сервером
на портах 80/443. Не удаляйте overlay входа из действующего запуска.

## Обычные операции

```sh
cd /opt/signage-editor/releases/20261009-vps8/vps-project
docker compose -f compose.host-proxy.yaml -f compose.password.yaml ps
docker compose -f compose.host-proxy.yaml -f compose.password.yaml config --quiet
docker compose -f compose.host-proxy.yaml -f compose.password.yaml logs --tail=80 app
docker compose -f compose.host-proxy.yaml -f compose.password.yaml exec app python deploy/check-runtime.py --require-login
```

Перезапуск затрагивает только редактор:

```sh
docker compose -f compose.host-proxy.yaml -f compose.password.yaml restart app
```

Сначала дождитесь окончания текущей генерации. При штатной остановке сервер
ждёт завершения задания до 930 секунд, Compose — до 16 минут. Принудительное
завершение или перезагрузка VPS могут прервать запрос; повтор автоматически
не отправляется. История и авторизация хранятся в томах и переживают замену
контейнера. Не выполняйте команды удаления томов (`down -v`) и не удаляйте
эти тома. Закрытый файл входа находится вне контейнера и должен сохраняться
отдельно от исходного выпуска.

## Пароль редактора: создание и смена

В `.env` действующего выпуска должны быть заданы `DOMAIN=vm-app.ru`,
`APP_VERSION=20261009-vps8` и `EDITOR_AUTH_HOST_FILE` — абсолютный путь к закрытому
файлу. `EDITOR_PUBLIC_ORIGIN` получается как `https://vm-app.ru`, без `/signs/`.
Путь `/signs/` находится в конфигурации cookie и правилах прокси.
В этом выпуске исходный путь — `/opt/signage-editor/private/editor-auth.json`,
файл принадлежит `10001:10001`, права `0400`; родительский каталог принадлежит
root и закрыт правами `0700`. При следующей смене пароля используйте новый
путь, как в примере ниже.

Для нового пароля создавайте **новый файл**, затем переключайте приложение на
него. Не записывайте пароль в shell-команду, `.env` или исходник. Следующие
команды выполняются администратором; после каждой проверьте успешное завершение:

```sh
cd /opt/signage-editor/releases/20261009-vps8/vps-project
umask 077
install -d -m 700 /opt/signage-editor/private
auth_dir="$(mktemp -d /opt/signage-editor/private/auth-XXXXXXXX)"
python3 scripts/editor_auth.py create \
  --output "$auth_dir/editor-auth.json" --cookie-path /signs/
chown 10001:10001 "$auth_dir/editor-auth.json"
chmod 0400 "$auth_dir/editor-auth.json"
```

Введите новый пароль дважды в интерактивном запросе. Скрипт использует только
стандартную библиотеку Python, записывает PBKDF2-хеш со случайной солью и секрет
подписи сессий; открытого пароля в файле нет. При создании файл имеет `0600`,
затем получает UID/GID 10001 и права `0400` для чтения приложением. Родительские
каталоги доступны только root; Docker монтирует сам файл по абсолютному
пути. Конфигурация не должна принадлежать root с правами `0400` внутри
контейнера: пользователь приложения тогда не сможет её прочитать.

В `.env` замените только `EDITOR_AUTH_HOST_FILE` на созданный абсолютный путь.
Сохраните остальные настройки и права `.env` `0600`. Дождитесь окончания
генерации и примените конфигурацию:

```sh
docker compose -f compose.host-proxy.yaml -f compose.password.yaml config --quiet
docker compose -f compose.host-proxy.yaml -f compose.password.yaml up -d --force-recreate --no-build app
docker compose -f compose.host-proxy.yaml -f compose.password.yaml ps
```

`restart` сам по себе не подхватывает изменённый bind mount или `.env`;
для нового пути нужен `up --force-recreate`. Проверьте вход с новым паролем
в отдельном окне браузера и отказ старой cookie. Новая конфигурация аннулирует
старые сессии. Некорректный файл должен остановить запуск, а не открыть доступ.
Прежний файл сохраняйте закрыто до проверки; не включайте оба файла в архив
проекта или истории. Для отката только пароля верните прежний путь и пересоздайте
контейнер, понимая, что прежние сессии могут снова стать действительными.

Cookie имеет `Secure`, `HttpOnly`, `SameSite=Strict`, путь `/signs/` и срок
12 часов. Вход не требует логина. После пяти неверных попыток за минуту
приложение временно ограничивает попытки для всего экземпляра и возвращает
`429` с `Retry-After`. Не создавайте автоматический цикл проверки пароля.

Codex и не входит в архив истории. API-ключи не используются.

проверка окружения сама по себе не подтверждает доступ к imagegen, лимит
подписки или совместимость sandbox с фактическим запросом. Не включайте
автоматические повторы ошибки.

## Резервная копия истории

Перед подготовкой vps5 сохранён снимок
`/opt/signage-editor/backups/history-before-vps5-20261009.zip`: 10 заданий,
122 файла, 111 864 885 распакованных байт. История продолжает расти; перед
следующим обновлением создавайте свежую копию. Архив на странице передачи
`history-handoff-20261008.zip` остаётся отдельным снимком 7 заданий.

Дождитесь завершения заданий. Архив содержит исходные фотографии и параметры,
поэтому сохраняйте его за пределами каталогов, опубликованных веб-сервером.

```sh
cd /opt/signage-editor/releases/20261009-vps8/vps-project
umask 077
install -d -m 700 /opt/signage-editor/backups
backup_name="history-$(date -u +%Y%m%dT%H%M%SZ).zip"
docker compose -f compose.host-proxy.yaml -f compose.password.yaml stop app
docker compose -f compose.host-proxy.yaml -f compose.password.yaml run --rm --no-deps app \
  python scripts/history_transfer.py export \
  --source /data/jobs --archive "/data/$backup_name"
docker compose -f compose.host-proxy.yaml -f compose.password.yaml cp \
  "app:/data/$backup_name" "/opt/signage-editor/backups/$backup_name"
chmod 600 "/opt/signage-editor/backups/$backup_name"
docker compose -f compose.host-proxy.yaml -f compose.password.yaml up -d app
```

Проверяйте успешный результат каждой команды, прежде чем выполнять следующую.
Если экспорт завершился ошибкой, запустите приложение командой `up -d app` и
разберитесь с ошибкой; такой архив нельзя считать готовой копией. Сохраните
полученный файл вне VPS. Экспорт добавляет SHA-256 каждого файла и отказывается
перезаписывать существующий архив.

## Восстановление истории

Полную копию восстанавливайте в новый пустой том при восстановлении сервера.
Импорт в действующую историю отклоняет совпадающие идентификаторы заданий;
он не перезаписывает старые изображения. Не удаляйте текущий том ради импорта.
Для отдельного чистого экземпляра сначала подготовьте конфигурацию и тома,
а затем используйте следующий пример, заменив имя архива:

```sh
install -d -m 700 /opt/signage-editor/private
restore_dir="$(mktemp -d /opt/signage-editor/private/restore-XXXXXXXX)"
install -o 10001 -g 10001 -m 0400 \
  /opt/signage-editor/backups/ИМЯ-АРХИВА.zip "$restore_dir/history.zip"
docker compose -f compose.host-proxy.yaml -f compose.password.yaml stop app
docker compose -f compose.host-proxy.yaml -f compose.password.yaml run --rm --no-deps \
  -v "$restore_dir/history.zip:/backup/history.zip:ro" \
  app python scripts/history_transfer.py import \
  --archive /backup/history.zip --destination /data/jobs
docker compose -f compose.host-proxy.yaml -f compose.password.yaml up -d app
```

`mktemp` создаёт новый закрытый каталог для каждого восстановления; существующая
копия не перезаписывается. Оригинал остаётся у root с правами `0600`. Файл для
импорта принадлежит UID/GID 10001 и имеет права `0400`, поэтому приложение
может прочитать его через привязку только для чтения. Родительский каталог
на хосте остаётся доступен только root. Не запускайте импорт от root внутри
контейнера: восстановленные задания должны принадлежать пользователю приложения.
Проверяйте успех создания каталога и копирования до остановки приложения.

Импорт проверяет контрольные суммы до публикации заданий. После него откройте
историю, исходники и готовые изображения. Перенесённые незавершённые задания
не отправляются на генерацию повторно. На новом сервере подключите подписку
заново; архив истории не содержит авторизации.

## Обновление приложения

Перед обновлением сохраните историю и текущий образ; новый выпуск разместите
в отдельном каталоге `/opt/signage-editor/releases/`. Сохраните имя проекта
`signage-editor`, имена томов, порт 18880 и `DOMAIN=vm-app.ru`. Менять DNS,
конфигурацию других сайтов и существующую авторизацию Codex для обычного
обновления редактора не требуется. Сохраните оба файла Compose и правильный
`EDITOR_AUTH_HOST_FILE`; иначе новый запуск не будет эквивалентен действующему.
В `DOMAIN` и `EDITOR_PUBLIC_ORIGIN` путь `/signs/` не добавляется.

Первичный переход с vps1 на vps2 выполняется в такой последовательности:

1. Создайте конфигурацию пароля и настройте новый выпуск с обоими файлами
   Compose. Сохраните свежую копию Caddy и прежний образ.
2. Запустите vps2, пока Basic Auth в Caddy ещё защищает `/signs/*`. Убедитесь,
   что backend без cookie возвращает 401 для API и 303 для редактора, а
   пароль создаёт рабочую сессию.
3. Только после этой проверки замените **правило редактора** на шаблон
   `deploy/Caddyfile.password-path.example`, убрав прежний Basic Auth.
   Проверьте и перезагрузите Caddy, затем проверьте публичный вход и основной
   сайт. Остальные блоки Caddy сохраняются.

Переход vps2 → vps3 сохраняет вход, оба Compose-файла, файл пароля, тома и
маршрут `/signs/`. Переход vps3 → vps4 добавляет только интерактивную линейку
и её сохранение в проекте. В vps5 добавляются масштаб вида, локальный черновик и HTTP-выдача
пакета CorelDRAW. Сам CorelDRAW на Linux VPS не устанавливается: CDR создаётся
на Windows пользователя. Vps6 исправляет видимость эталонных точек и сброс
зависшего перемещения; формат проекта и геометрия экспорта сохраняются.
Vps7 задаёт для векторов CDR чёрный цвет по умолчанию отдельно от цвета
вывески на фото; это не требует миграции серверных данных.
Vps8 добавляет одноразовую передачу параметров в локальный CorelDRAW;
миграции данных нет. [Установка помощника Windows](docs/CORELDRAW.md).
**Caddy для этих переходов не меняется**, секреты
и тома остаются прежними. Для
обновлений сохраняйте тот же механизм входа. Новый выпуск
собирайте с новым `APP_VERSION`, проверяйте конфигурацию и перезапускайте только
`app` после завершения задания. Не удаляйте прежний образ до проверки новой
версии. История хранится отдельно в томе; смена образа её не откатывает.

## Предпочтительный откат vps8 → vps7

После завершения генерации и запросов Corel можно вернуть сохранённый образ:

```sh
cd /opt/signage-editor/releases/20261009-vps8/vps-project
APP_VERSION=20261009-vps7 docker compose -f compose.host-proxy.yaml -f compose.password.yaml up -d --no-build app
```

Проверьте вход, историю и основной сайт. Автоматическое открытие Corel станет
недоступно; ZIP и чёрные векторы сохранятся. История и локальные CDR не удаляются.
Для постоянного отката укажите тег vps7 в `.env`; для возврата — vps8.

Более ранний vps2 также поддерживает вход по cookie, но не содержит страницы
скачивания. Архивы в `/data/handoff` при смене образа сохраняются. Для отката
на vps1 действует отдельный обязательный порядок ниже.

## Особый случай: откат на vps1

**Нельзя просто запустить старый образ под нынешним Caddy.** У vps1 нет
встроенного входа по паролю, поэтому после удаления Basic Auth он стал бы
доступен публично, включая историю и API.

1. Сначала верните Basic Auth только в `handle_path /signs/*`. Используйте
   сохранённый предыдущий блок редактора либо `deploy/Caddyfile.path.example`
   с выбранным именем и действительным bcrypt-хешем. Пароль для прежнего
   Basic Auth — отдельный от нового файла приложения.
   Предыдущий блок есть в копии Caddy
   `/etc/caddy/Caddyfile.before-signage-password-20261008`; переносите из неё
   только нужные директивы редактора, не весь файл поверх текущего.
2. Выполните `caddy validate` и `caddy reload`. Убедитесь, что анонимные
   `/signs/` и `/signs/api/config` теперь возвращают 401 Caddy. Пока работает
   vps2/vps3/vps4/vps5/vps6/vps7/vps8, временно потребуются оба входа; это ожидаемо на этапе отката.
3. Дождитесь завершения генерации. Только после проверки защиты прокси
   переключите образ из текущего каталога с сохранёнными файлами Compose:

```sh
cd /opt/signage-editor/releases/20261009-vps8/vps-project
APP_VERSION=20261008-vps1 docker compose -f compose.host-proxy.yaml -f compose.password.yaml up -d --no-build app
```

Команда требует, чтобы старый образ оставался на сервере. Старый сервер
игнорирует `EDITOR_AUTH_FILE`, поэтому внешний Basic Auth обязателен. Закрытый
файл остаётся смонтирован только для чтения; это не создаёт авторизацию в vps1.
Проверьте основной сайт, защищённость `/signs/`, вход через Basic Auth, историю
и статус Codex. Содержимое томов не откатывается и не удаляется.
Если оставляете vps1 рабочей версией, также сохраните `APP_VERSION=20261008-vps1`
в `.env`: переменная перед командой выше действует только на один вызов,
и последующий `up` иначе снова выберет образ из `.env`.

При возврате с vps1 на vps2/vps3/vps4/vps5/vps6/vps7/vps8 сначала запустите и проверьте новый образ под защитой
Basic Auth, затем снова уберите Basic Auth только из блока редактора.

## Файлы для передачи проекта

`/signs/downloads.html` открывает защищённую страницу с тремя фиксированными
именами: `signage-editor-handoff.zip`, `history-handoff-20261008.zip` и
`SHA256SUMS-handoff.txt`. Прямые ссылки `/signs/downloads/<имя>` требуют cookie
входа, но не токен `X-Editor-Token`. Без сессии пользователь сначала попадает на
вход, затем на страницу скачивания. В публичном режиме без встроенной
авторизации эта выдача закрыта.

Файлы лежат в `/data/handoff` постоянного тома `signage-editor_data`, отдельно
от заданий. Их размещает администратор на хосте: каталог `root:root 0755`,
файлы `root:root 0444`, доступные приложению только для чтения. Не храните там
`.env`, файл пароля, SSH-ключи или содержимое тома Codex. Приложение не принимает
загрузку произвольных файлов в этот каталог.

Архивы — статический снимок. После обновления кода пересоберите исходный архив
без секретов, при необходимости отдельно экспортируйте историю и пересчитайте
`SHA256SUMS-handoff.txt`. Сначала подготовьте согласованный набор в закрытом
месте, затем замените публикуемые файлы, сохранив владение и права; не записывайте
частично готовый архив сразу под его окончательным именем. Скачайте файлы через
HTTPS и сравните SHA-256. Один и тот же `signage-editor-handoff.zip` в новом
выпуске имеет другой хеш. Изменение архива не требует повторной генерации.

## Caddy и удаление публикации редактора

Для vps2/vps3/vps4/vps5/vps6/vps7/vps8 шаблон `deploy/Caddyfile.password-path.example` вставляется **внутрь
существующего** блока `vm-app.ru`. Он добавляет перенаправление `/signs` →
`/signs/` и `handle_path /signs/*`, который удаляет префикс перед отправкой
приложению. Basic Auth здесь нет: его заменяет проверенный встроенный вход.
Шаблон допустим только при активном `EDITOR_AUTH_FILE`. Браузер сохраняет
префикс в запросах к API и изображениям; отдельная DNS-запись не нужна.

Прежний `deploy/Caddyfile.path.example` с Basic Auth сохранён для отдельного
размещения без встроенного входа и для безопасного отката. Не путайте шаблоны.

Перед изменением Caddy сохраните свежую копию его файла. Проверяйте **всю**
конфигурацию установленным на хосте Caddy; применяйте только после успеха:

```sh
caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
caddy reload --config /etc/caddy/Caddyfile --adapter caddyfile
```

Для снятия публикации уберите только перенаправление `/signs` и блок
`handle_path /signs/*`, затем проверьте и перезагрузите Caddy. После этого
можно остановить только приложение:

```sh
docker compose -f compose.host-proxy.yaml -f compose.password.yaml stop app
```

Не восстанавливайте старую копию Caddy поверх текущей целиком: после
первоначального размещения другие сайты могли получить свои изменения.
Сравнивайте с `/etc/caddy/Caddyfile.before-signage-20261008` и удаляйте только
настройки редактора. Остальные контейнеры и системный Caddy не останавливайте.

После любых изменений проверьте основной сайт и доступ редактора. Для vps2/vps3/vps4/vps5/vps6/vps7/vps8
без cookie ожидаются такие ответы:

| Адрес | Ожидаемый ответ |
| --- | --- |
| `/signs` | 308 → `/signs/` |
| `/signs/`, `/signs/calibrator.html`, `/signs/history.html` | 303 → страница входа с безопасным `next` |
| `/signs/login.html` и её JS/CSS | 200, без данных истории |
| `/signs/healthz` | 200 с минимальным статусом; не проверяет лимиты/генерацию |
| `/signs/api/config`, `/signs/api/history`, PNG через API | 401 с `auth_required:true` |
| `/signs/downloads.html`, `/signs/downloads/<разрешённый файл>` в vps3/vps4/vps5/vps6/vps7/vps8 | 303 → вход → страница передачи |

После ввода пароля проверьте открытие интерфейса, истории и изображения через
авторизованный интерфейс. API, кроме `/api/config`, дополнительно требует
`X-Editor-Token`; одна cookie при прямом открытии PNG в новой вкладке не
заменяет токен. Сравните основной сайт с состоянием до изменения редактора.
Не создавайте новую генерацию только ради проверки входа.
