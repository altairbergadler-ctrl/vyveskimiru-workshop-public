# Регулярная разработка Мастерской

Устройство системы и бизнес-границы — [ARCHITECTURE.md](../ARCHITECTURE.md).
Короткие правила для разработчиков и помощников — [AGENTS.md](../AGENTS.md).

## Начало работы и единая проверка

Работать внутри `finance-pwa-2026-08-30` в отдельной короткой ветке.
Нужны Node.js 22 (не ниже 22.13), npm и Python 3.9+ для проверок процедур выпуска.
На Linux сборка `better-sqlite3` при отсутствии готового бинарника требует make/g++.

```sh
npm ci
npm run setup
npm run check
```

`setup` включает только локальный Git pre-commit hook этого репозитория.
`check` последовательно запускает содержательные тесты финансов/заказов/склада/
производства и инфраструктуры, TypeScript, lint и сборку. После установки зависимостей
тесты обходятся без рабочих ключей и запросов в Google. Тест HTTP-сервера имеет
вымышленный Google-клиент; исходящие вызовы fetch в нём запрещены.

Lint охватывает `app`, `components`, `hooks`, `lib`, `src`, `server`, оба раздела
`modules/orders`, `public`, `qa` и Vite-конфигурацию. В `qa/lint-baseline.json`
зафиксированы 62 замечания прежнего кода, ранее не охваченного проверкой. Это
технический долг, а не отсутствие замечаний. Любое новое замечание блокирует
проверку; старое сопоставляется с файлом, правилом, сообщением и SHA256 строки.
Изменение строки прекращает действие исключения. Не расширять baseline для
прохождения новой задачи. Удалять записи по мере исправления старого кода.
Next.js-плагин исключён: приложение собирается Vite, а не Next.js.

`.github/workflows/check.yml` выполняет эту же проверку при push и pull request.
В этом локальном репозитории пока нет remote: внешние запуски начнутся после
подключения GitHub. Там же нужно сделать `Workshop check / check` обязательным
для слияния. Это внешняя настройка владельца; локальный hook уже подключён.
Независимо от GitHub, Docker-сборка обычного выпуска обязательно выполняет `check`.

## Временный локальный стенд

### Производство для обратной связи

В ветке `production-pilot` после `npm run check`:

```sh
npm run production:preview
# Остановка с сохранением вымышленных заказов и результатов:
npm run production:stop
# Проверка реального интерфейса на собственном временном наборе:
node qa/production-browser.mjs
```

`production:preview` печатает `/open` для руководителя и адрес личного входа
мастера. Контроллер слушает только localhost и открывает учебную сессию.
Повторный запуск сохраняет данные: `work/sandbox/production-preview.json`
указывает на принадлежащий этому стенду каталог `production-feedback-*`.
`production-control.json` содержит секрет управления: его содержимое не выводить.
После аварии сначала проверить записанные PID, затем восстановить собственный
стенд; новый экземпляр поверх работающего автоматически не создаётся.

Для пробы: получить материалы и начать задачу на экране мастера; указать
частичное выполнение и проверить личную историю; поменять назначение/порядок
в плане; отредактировать продукт и добавить его в учебный заказ. Для личного
входа открыть «Мастера → Компетенции и доступ», задать код, включить доступ
и сохранить профиль. Проверять личный вход в отдельном профиле/приватном окне,
поскольку сессия руководителя в обычном окне имеет приоритет.

Предустановленные смены намеренно покрывают почти весь день, чтобы пробовать
стенд в любое время. Сроки создаются при первом запуске; обычный перезапуск
не переносит их и не стирает результаты. Обязательный день можно изменить
в назначении задачи. Для полностью нового набора есть одноразовый вариант
`npm run sandbox:start -- --production`, с отдельными reset/stop; его остановка
удаляет только собственный временный каталог по прежнему контракту.

В `qa/production-pilot.test.mjs` проверены серверные роли, повтор команд,
сохранение после перезапуска, частичное и полное закрытие заказа через реальную
операцию общей доски, ошибка подтверждения и повтор. `production-browser.mjs`
создаёт собственный изолированный набор, проверяет ширину 1440/384, вкладки,
редактор, выдачу/запуск, изображения, личный вход, частичное выполнение и историю.
Снимки и отчёт остаются в `work/validation/production`; тестовый сервер и его
каталог удаляются после проверки. Playwright берётся из `PLAYWRIGHT_MODULE`
или локального bundled runtime, браузер — установленный Edge.

### Обычный одноразовый стенд

После `npm run check`:

```sh
npm run sandbox:start
# В другом терминале:
npm run sandbox:reset
npm run sandbox:stop
```

Первая команда показывает локальную ссылку `/open`: она открывает вымышленную
Мастерскую с тестовой сессией, без вывода PIN и cookie. После сброса снова открыть
эту ссылку. Сервер слушает только 127.0.0.1; настоящие ключи и настройки не наследуются.
В наборе — два вымышленных клиента, два заказа, платёж, расход, материал и этап.
Для проверки главной используйте `npm run sandbox:start -- --widgets`:
восемь вымышленных заказов с разными сроками/статусами, монтажи и согласование,
доступный и ожидающий этапы, три материала с недостатком и потреблением.
Даты набора считаются относительно дня запуска. `npm run sandbox:reset`
пересоздаёт набор, выбранный при старте; для переключения набора остановите
стенд и запустите снова с нужным флагом. Сохранённые данные экземпляра
не подменяются при обычном входе.
Данные находятся в уникальном `work/sandbox/manual-*`. Сброс стирает только данные
этого экземпляра, остановка — его каталог. Соседние запуски защищены маркером и
проверкой реального пути. При аварийном закрытии сначала проверить PID из локального
`control.json`; не удалять вслепую каталог другого процесса.

Это настоящий HTTP-сервер и интерфейсы, но Google подменён небольшим транспортом
с примерами рассчитанных значений. Здесь проверяются чтение, вход, финансовые
команды, повторы и перезапуск. Пересчёт формул, создание подготовленных строк и
полная приёмка всех записей требуют отдельной Google Таблицы. Эмулятор не обещает
реализовать весь Google API; неподдерживаемые операции отклоняются.

## Интеграция с Google

Разрешена только тестовая копия `EXAMPLE_TEST_GOOGLE_SHEET_ID_CHANGE_BEFORE_USE`.
Рабочая таблица и нативная резервная копия запрещены в `qa/safety.mjs`; одного URL
стенда недостаточно. `GOOGLE_SPREADSHEET_ID` и `QA_CONFIRM_SHEET` должны точно
совпадать с разрешённым ID. Другой ID требует осознанного изменения allowlist.

Отдельный Node-процесс/тестовый контейнер запускается с
`NODE_OPTIONS=--import=/app/qa/integration-preload.mjs`. До запуска сервера preload
проверяет ID, подтверждение, маркер `.workshop-qa` со значением `workshop-qa-v1`
в `QA_DIRECTORY` и собственный `DATA_DIR=QA_DIRECTORY/data`. Ключ монтируется
только для чтения, извне репозитория. Никаких рабочих `app.env` на стенде.

В этом окружении `npm run test:integration` проверяет четыре раздела, создаёт один
вымышленный расход, повторяет тот же requestId, убеждается в единственности и
удаляет только созданный расход, сравнивая реальные формулы его строки до/после.
Runner принимает только loopback `QA_BASE_URL`, сверяет точный ID ответа backend
до записи, удаляет собственную сессию в finally и сохраняет отчёт/квитанции в
`QA_DIRECTORY`. При неопределённом ответе сохранить это состояние для разбора,
не повторять запрос с новым ID. Полный сброс тестовой Google копии не выполняется.

Расширенная историческая приёмка `qa/acceptance.cjs` теперь требует явных
`QA_BASE_URL`, `QA_DATABASE` внутри `/opt/workshop-qa/run-*`, Google ID и подтверждения.
Дополнительно: `QA_SSH_HOST`, `QA_REPORT_DIR`, `PLAYWRIGHT_MODULE`, `QA_BROWSER_PATH`;
для сценария входа `QA_PIN` передаётся приватно. Playwright и его браузер нужны
только для этой расширенной приёмки. `--production-read-only` запрещает бизнес-записи.

## Обычный выпуск и откат

Производство v2: `PRODUCTION_V2=google` включается рабочим compose. После полной
копии и остановки прежнего writer установщик выполняет `server/production-migrate.mjs
--apply`. Скрипт делает единый атомарный импорт в новый лист и не заменяет
существующий лист при повторе. Для read-only аудита запустить без `--apply`.
Не включать этот флаг вручную на старом выпуске без готового листа.
После подтверждённых команд v2 откат на старое производство запрещён контрактом
выпуска; совместимый откат сохраняет текущие данные. Pending-команды не удалять.

Реальная Google-проверка нового процесса: `qa/production-integration.mjs`, только
при совпадении TEST_SHEET/QA_CONFIRM_SHEET и маркере собственного QA-каталога.
Она переносит копию, создаёт собственные вымышленные записи, проверяет выдачу,
частичное выполнение, повтор и готовность заказа. Все изменённые поля журналируются
и возвращаются к прежним значениям с проверкой; удаляется только новый лист,
созданный этим запуском. При неподтверждённой выдаче данные остаются для разбора.
Перед этой проверкой используется существующее выравнивание `contract-copy.mjs`;
его оригинальные формулы обязательно восстанавливаются после теста.

```sh
npm run release:pack
```

Команда требует чистый закоммиченный Git, выполняет `check`, создаёт архив HEAD,
файл `.sha256` и `.revision` в `work/releases`. Передать три файла на VPS, затем:

```sh
bash deploy/install-workshop.sh FULL_SHA /path/FULL_SHA.tar.gz
```

Использовать скрипт из нового проверенного исходника. Установка применима только
к уже объединённому backend; права нужны для Docker, shared и Caddy. Алгоритм:
проверить архив/команды → собрать образ с полной проверкой → включить обслуживание
только Мастерской → остановить и дождаться текущего писателя → повторно проверить
квитанции → создать и проверить полную свежую копию → включить новый образ →
дождаться здоровья именно его SHA → вернуть маршруты и выполнить диагностику.
Один локальный flock исключает одновременные выпуск, откат и резервирование.

Копия содержит Google с формулами/оформлением, SQLite, текущие файлы/квитанции,
код, настройки и рабочую конфигурацию обслуживания. Она не зависит от наличия
старых каталогов канбана и CRM. Их прежние полные архивы сохраняются отдельно.
Маркер COMPLETE появляется после контрольных сумм; проверяются возраст от начала,
дата окончания, выпуск, SHA256, наличие листов и целостность SQLite. Перед
переключением возраст не больше 15 минут. Ежедневный backup продолжает вызываться
существующим `finance-pwa-backup.timer`; `check-latest-backup.sh` проверяет свежесть
последней копии (26 часов). Внешнее назначение новых копий ещё не выбрано.

Установщик выводит каталог checkpoint. Ручной откат:

```sh
bash CHECKPOINT/procedure/rollback-workshop.sh CHECKPOINT
```

Откат также блокирует неподтверждённые команды, создаёт копию и проверяет старый
образ после запуска. Возвращается только код. Текущие Google-записи, SQLite-квитанции
и вложения не заменяются архивом. При неудаче нового выпуска предпринимается
автоматический возврат предыдущего кода. Если неподтверждённая команда мешает
безопасному возврату, сохраняются обслуживание и checkpoint для разбора.
Несовместимая миграция технической схемы требует отдельного плана; этот процесс
предполагает совместимость обоих объединённых выпусков с текущими данными.

`migrate-unified-workshop.sh` и `rollback-migration.sh` — сохранённая разовая миграция
из прежних сервисов. Для регулярных выпусков их не применять.

## Проверка самой процедуры

### Проверка контракта Google

Обычный `npm run check` включает отказы схемы/транспорта и квитанций, а также
запуск настоящего backend на вымышленных данных. Эмулятор хранит формулы и
примеры вычисленных значений раздельно; он не заменяет Google-пересчёт.

Для отдельной приёмки нового контракта `qa/sheets-contract-smoke.sh` использует
существующий совместимый runtime-образ и монтирует проверенный исходник только
для чтения. Это применимо при неизменных runtime-зависимостях; тест не является
обычным выпуском. В собственном `/opt/workshop-qa/run-NAME/source` должны быть
`server`, `modules/orders/server`, `qa`, собранный `dist`. У каталога `run-NAME`
нужен обычный маркер `.workshop-qa` со значением `workshop-qa-v1`.

```sh
WORKSHOP_QA_ROOT=/opt/workshop-qa/run-NAME \
GOOGLE_SPREADSHEET_ID=EXAMPLE_TEST_GOOGLE_SHEET_ID_CHANGE_BEFORE_USE \
QA_CONFIRM_SHEET=EXAMPLE_TEST_GOOGLE_SHEET_ID_CHANGE_BEFORE_USE \
bash qa/sheets-contract-smoke.sh COMPATIBLE_RUNTIME_IMAGE /path/to/read-only-google-key.json
```

Тест проверяет финансовый HTTP-путь, создание клиента/заказа/позиции/монтажа,
каталог и движения. Исходные ячейки ограниченных тестовых записей журналируются
до записи и восстанавливаются точно. Затем временно портятся один заголовок
и одна формула: ожидаются отказ HTTP, плохая диагностика и отсутствие ожидающей
команды. Эти две ячейки восстанавливаются в `finally`. Старые 300 формул
тестовой копии возвращаются внешним обработчиком завершения; после остановки
контейнера исходная копия снова отличается от рабочего контракта границей 497.
Продуктивная таблица и нативный резерв запрещены жёстким allowlist.

Один ключ Google имеет общую квоту: runner ограничивает темп запросов и не повторяет
неизвестно завершившиеся записи. При прерывании процесса сначала изучить
`contract-write-journal.json`, `contract-fault-journal.json` и
`contract-copy-formulas.json` в собственном каталоге. Не запускать поверх
незавершённого журнала и не удалять доказательства до подтверждения восстановления.
После приёмки сохранить отчёты локально, затем убрать свой временный контейнер
и проверенные каталоги. Новые образы и build cache для этого теста не создаются.

### Выпуск и откат

Пополнение склада отдельно проверяется `qa/refill-smoke.sh` с теми же
`WORKSHOP_QA_ROOT`, `GOOGLE_SPREADSHEET_ID`, `QA_CONFIRM_SHEET`, образом и ключом,
что и проверка контракта выше. Для этого runner достаточно каталогов `server` и
`qa` внутри `source`. Он создаёт вымышленный материал без начального движения,
отправляет одно пополнение, теряет ответ и чтение результата, заново открывает
SQLite и проверяет повтор без второй записи. `refill-report.json` фиксирует
результат; `contract-write-journal.json` и журнал временных формул сохраняются
до точного восстановления. Источник подключается только для чтения, порты
не публикуются, новый образ не создаётся.

Локальный стенд умеет воспроизводить сбой пополнения: файл `refill-fault` в его
собственном каталоге со значением `lost-response` теряет ответ после записи и
создаёт `refill-readback-failed`; `before-write` оставляет неопределённый результат
без изменения таблицы. Удаление этих собственных файлов возвращает чтение.
Само пополнение не переотправляется. Автоматический HTTP-тест проверяет
перезапуск сервера; ручная браузерная проверка — восстановление формы и вкладок.

При выпуске/откате квитанции `warehouse_refills` должны быть завершены. После
первой квитанции (даже `confirmed`) старый целевой выпуск без
`server/release-capabilities.json` с `warehouseRefillReceipts: 1` недопустим:
браузер может повторить уже подтверждённый запрос после потери HTTP-ответа.
Всегда применять актуальные скрипты из нового выпуска или его checkpoint,
а не исторические процедуры до защиты пополнений. Не удалять квитанции для
обхода проверки; они сохраняются вместе с текущей SQLite-базой.

На Linux-хосте с Docker создать новый `/opt/workshop-qa/run-NAME`, записать в нём
маркер `.workshop-qa` и запустить:

```sh
WORKSHOP_QA_ROOT=/opt/workshop-qa/run-NAME WORKSHOP_QA_PORT=18260 bash qa/release-smoke.sh
```

Тест проходит настоящий Docker build/up/stop, успешный выпуск, запрет отката при
резервированной команде, откат с сохранением новой операции/файла, автоматический
откат после плохого health и отказ теста до остановки текущего контейнера.
Проверяется распаковка полной копии. Только тестовый профиль разрешает подмену
Google и пути, проверяя владельца каталога. Контейнер запускается с network=none; HTTP-проверки идут внутри контейнера.
Тест удаляет созданный контейнер, сети и именованные образы даже при ошибке.
Каталог с отчётами и копиями сохраняется для проверки; после переноса доказательств
удалить только этот проверенный каталог. Не применять общую очистку Docker.
